CS336 Project 2 - Functional Dependencies (Canonical Cover)

1NF naming notes:
- application_id is the generated application key populated from Project 1's
  sequence_number values.
- applicant_race_number and applicant_race_code correspond to race_number and
  race_code in the applicant_race table.
- co_applicant_race_number and co_applicant_race_code correspond to race_number
  and race_code in the co_applicant_race table.
- denial_reason_number and denial_reason_code correspond to reason_number and
  denial_reason_code in the application_denial_reason table.
- The original numbered race and denial-reason columns are removed by the 1NF
  transformation.
- applicant_ethnicity and co_applicant_ethnicity both use the ethnicity code
  domain, so their two FDs below are stored in one shared ETHNICITY table
  (ethnicity_code -> ethnicity_name). Likewise applicant_sex and co_applicant_sex
  share one SEX table (sex_code -> sex_name), and both race join tables share one
  RACE table.

Extra table justification:
- RESPONDENT (agency_code, respondent_id) is the one table not required by an FD.
  We keep it because a reporting institution is a real entity identified by the
  PAIR (agency_code, respondent_id): respondent_id alone does not determine
  agency_code (see Excluded dependencies). The foreign key from application to
  respondent rejects any application whose agency/respondent pair does not exist.

Excluded dependencies:
- {respondent_id} -> {agency_code} is false in the CSV. Respondent IDs
  0000025093 and 0000013879 each occur under agency codes 1 and 3.
- No dependency is inferred solely because as_of_year, state_code, or another
  attribute is constant in this particular 2017 New Jersey data instance.
- No finer geographic dependency is included because the project handout says to
  treat the complete ten-column location set as the location candidate key.
